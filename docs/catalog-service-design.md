# Как могут выглядеть сервисы каталога отелей и номеров

Это предложение следующего этапа разработки под R1. Имена файлов, классы и примеры
ниже показывают будущую реализацию: самого catalog_service в проекте пока нет.
Документ опирается на текущее разделение слоёв и требования ТЗ.

## 1. Один микросервис, несколько классов сервисного слоя

Для начала предлагаю один **catalog_service** с собственной PostgreSQL-базой.
Внутри него будут HotelService, RoomService, RateService и поиск по каталогу.
Это разные Python-классы внутри одного приложения FastAPI.

Отель, номер и тариф тесно связаны. Общая БД позволяет проверить существование
отеля и создать номер в одной транзакции, использовать внешние ключи и получать
карточку без нескольких сетевых запросов между микросервисами.

```text
gateway
  ├── user_service       пользователи, пароли, JWT и refresh-сессии
  ├── catalog_service    отели, номера, тарифы, фото, справочники, поиск
  └── booking_service    бронирования и доступность на даты — следующий этап
```

Внутри каталога сохраняем знакомую цепочку:

```text
HTTP-роут → HotelService / RoomService / RateService → Repository → AsyncSession
```

## 3. За что отвечает каждый сервис

| Класс | Операции | Основные проверки |
| --- | --- | --- |
| HotelService | Создать отель, получить карточку, изменить, деактивировать | Существование, активность, корректность полей |
| RoomService | Создать номер в отеле, получить, изменить, деактивировать | Отель существует и активен; вместимость и цена допустимы |
| RateService | Создать и изменить тариф, получить тарифы номера | Номер существует; цена и условия корректны |
| CatalogSearchService | Найти отели по условиям, посчитать total и сформировать страницу | Даты, гости, номера, значения справочников, сортировка |

Роут разбирает HTTP-запрос, подключает зависимости и возвращает response_model.
Сервис применяет бизнес-правила и управляет транзакцией. Репозиторий выполняет SQL
и возвращает ORM-объекты или специально сформированные результаты выборки.

## 4. Пример моделей

Идентификаторы новых сущностей предлагаю сразу сделать UUID, как в ТЗ.

| Модель | Основные поля |
| --- | --- |
| Hotel | id, name, description, city, address, latitude, longitude, rating, tags, is_active, created_at, updated_at |
| Rating | id, hotel_id, user_id, value, description |
| Room | id, hotel_id, name, description, capacity, price, tags, is_active, created_at, updated_at |
| Rate | id, room_id, name, price, currency, breakfast_included, cancellation_policy, conditions, is_active |
| Photo | id, hotel_id или room_id, url, sort_order |
| InteriorStyle | id, code, name, is_active |
| BookingPurpose | id, code, name, is_active |
| RoomInteriorStyles| id, room_id, style_id |
| RoomInteriorPurposes| id, room_id, purpose_id |

Связи Hotel → Room и Room → Rate — один ко многим, с внешними ключами в БД каталога.
Цена хранится как NUMERIC/Decimal. Для MVP можно зафиксировать RUB и цену за ночь.
Итог бронирования рассчитывается на backend по выбранному тарифу и датам.

Поле Room.price из ТЗ можно оставить базовой ценой для отображения. При оформлении
используется цена выбранного Rate: клиентская цена не считается доверенной.
В поиске отображаем минимальную подходящую цену и явно называем её «от ...».

Рейтинг отеля — поле для чтения, которое рассчитывается из отзывов. Его не нужно
принимать из обычного пользовательского PATCH отеля. Фото храним как ссылки;
двоичные файлы впоследствии можно размещать в объектном хранилище.
Для Photo стоит потребовать ровно одного владельца: отель или номер.

### Совместимость с текущим BaseRepository

Общий репозиторий обращается к model.id. Поэтому в Python можно оставить атрибут id,
а в PostgreSQL назвать колонку hotel_id, room_id или rate_id:

```python
class Hotel(Base):
    __tablename__ = "hotels"

    id: Mapped[UUID] = mapped_column("hotel_id", primary_key=True, default=uuid4)
```

Внешний ключ номера тогда указывает на hotels.hotel_id. В response-схеме поле
hotel_id можно получить из ORM-атрибута id через Pydantic validation_alias.
Так внешний JSON соответствует ТЗ, а общий репозиторий продолжает работать.

### Что считать номером

Это решение нужно принять до реализации доступности. В ТЗ одновременно есть
room_id и rooms_count, но не определено, является Room физическим экземпляром
или категорией одинаковых номеров.

Предлагаемый вариант для R1: Room — категория, например «Двухместный стандарт».
capacity — вместимость одного экземпляра. BookingService хранит остатки экземпляров
этой категории по датам и учитывает rooms_count. При одной категории в бронировании
базовая проверка вместимости: guests_count <= capacity * rooms_count.

Счётчик свободных экземпляров не должен определяться полем is_active каталога.
Изменение количества продаваемых номеров согласуется с владельцем остатков
в booking/inventory, чтобы не уменьшить вместимость ниже уже принятых броней.

## 5. Схемы запросов и ответов

Для каждой сущности нужны отдельные схемы:

```text
HotelCreate  → вход административного создания
HotelUpdate  → частичное изменение разрешённых полей
HotelRead    → публичные поля отеля
HotelDetail  → HotelRead + фото + отзывы + подходящие номера

RoomCreate   → вход создания номера в конкретном отеле
RoomUpdate   → частичное изменение номера
RoomRead     → публичные поля номера
RoomDetail   → RoomRead + фото + активные тарифы

RateCreate / RateUpdate / RateRead
SearchQuery / SearchItem / SearchResponse
```

hotel_id для создания номера лучше брать из URL. Клиент не должен отдельно
передавать второй hotel_id в теле, который может противоречить пути запроса.
UUID, даты, ограничения чисел и длины строк проверяют Pydantic-схемы.
Существование связанного отеля или номера проверяет сервис через репозиторий.

Пример ответа поиска — это предлагаемый контракт, который ещё предстоит закрепить:

```json
{
  "items": [
    {
      "hotel_id": "6a623958-bfc7-4bc8-97d9-d21c9c80e0e4",
      "name": "Отель у парка",
      "city": "Москва",
      "rating": "4.7",
      "min_price": "6500.00",
      "currency": "RUB",
      "tags": ["wifi", "parking"],
      "preview_photo_url": "https://example.com/hotel.jpg"
    }
  ],
  "total": 1,
  "page": 1,

```

При пустом результате возвращаем 200 с items=[] и total=0, без ошибки 404.

## 6. HTTP API и доступ

Ниже — целевые внешние пути из ТЗ. Текущий gateway пока использует
/api/{service}/{path}; переход к /api/v1 нужно выполнить отдельно.
Внутри catalog_service префикс /api/v1 не нужен: например, GET /hotels/{hotel_id}.

| Метод | Внешний путь | Доступ |
| --- | --- | --- |
| GET | /api/v1/hotels/search | Гость |
| GET | /api/v1/filters | Гость |
| GET | /api/v1/hotels | Гость; страница каталога |
| GET | /api/v1/hotels/{hotel_id} | Гость |
| GET | /api/v1/hotels/{hotel_id}/rooms | Гость |
| GET | /api/v1/rooms/{room_id} | Гость |
| POST | /api/v1/hotels | Администратор или отдельный доверенный import API |
| PATCH, DELETE | /api/v1/hotels/{hotel_id} | Администратор |
| POST | /api/v1/hotels/{hotel_id}/rooms | Администратор |
| PATCH, DELETE | /api/v1/rooms/{room_id} | Администратор |
| POST | /api/v1/rooms/{room_id}/rates | Администратор; предлагаемый дополнительный маршрут |
| PATCH, DELETE | /api/v1/rates/{rate_id} | Администратор; предлагаемые дополнительные маршруты |

GET /hotels/search нужно зарегистрировать раньше /hotels/{hotel_id}, чтобы слово
search не разбиралось как идентификатор. Параметры дат для карточки и списка номеров
позволят показывать подходящие варианты для выбранного периода.

DELETE для отеля, номера и тарифа означает деактивацию: is_active=false.
Физически записи, на которые ссылаются бронирования, не удаляем.
Публичные выборки исключают неактивные объекты и номера неактивных отелей.
Исторические данные для уже созданных броней доступны через отдельный закрытый API.

### Как здесь работает авторизация

Для гостевых GET JWT не требуется. В gateway нужно явно разрешить соответствующие
методы и шаблоны путей. В нынешнем PUBLIC_ROUTES хранятся точные строки, поэтому
добавить туда буквальную строку hotels/{hotel_id} недостаточно: реальные UUID с ней
не совпадут. Нужны явные роуты gateway или корректный матчинг разрешённых шаблонов.
Все остальные методы и пути должны оставаться закрытыми по умолчанию.

Для административной записи цепочка такая:

```text
gateway проверяет пользовательский access JWT
    → передаёт подписанное подтверждение личности и полномочий
    → catalog_service проверяет внутренний токен и административное право
    → вызывает HotelService / RoomService / RateService
```

**Сейчас административных ролей в проекте ещё нет.** Существующий внутренний токен
содержит user_id и session_id: он подтверждает личность, но не право менять каталог.
Нельзя разрешать запись любому пользователю только потому, что токен подписан gateway.

Перед открытием административных маршрутов нужно добавить серверную модель ролей
или permissions, например catalog:write. User-service получает полномочия из своей БД,
gateway передаёт проверенные claims во внутреннем JWT, а каталог проверяет требуемое
право. Альтернатива — отдельный закрытый административный вход. До этого запись
должна быть доступна только локальным seed-скриптам или полностью закрыта.

Каталог сам не выпускает пользовательские JWT и не устанавливает auth-cookies.
Ему нужен публичный ключ gateway; приватный ключ auth ему не нужен.
Если сохраняем текущую cookie-схему, gateway проверяет Origin и CSRF на изменениях.
Bearer-контракт из ТЗ следует согласовать с этой схемой до подключения клиента.

## 7. Пример передачи сессии через Depends и сервис

Сессия создаётся так же, как в user_service: dependency использует существующий
Database.get_session(), а затем передаёт AsyncSession репозиториям.

```python
# dependencies.py — пример будущей сборки зависимостей
def get_room_service(session: SessionDep) -> RoomService:
    return RoomService(
        hotels=HotelRepository(session),
        rooms=RoomRepository(session),
    )
```

```python
# services/rooms.py
class RoomService:
    def __init__(self, hotels: HotelRepository, rooms: RoomRepository):
        self.hotels = hotels
        self.rooms = rooms
        self.session = rooms.session

    async def create(self, hotel_id: UUID, data: RoomCreate) -> Room:
        async with self.session.begin():
            hotel = await self.hotels.read(hotel_id)
            if hotel is None or not hotel.is_active:
                raise HotelNotFoundError()

            return await self.rooms.insert({
                **data.model_dump(),
                "hotel_id": hotel_id,
            })
```

```python
# api/rooms.py — административная зависимость пока только проектируется
@router.post(
    "/hotels/{hotel_id}/rooms",
    response_model=RoomRead,
    status_code=201,
    dependencies=[Depends(require_catalog_write)],
)
async def create_room(
    hotel_id: UUID,
    data: RoomCreate,
    service: Annotated[RoomService, Depends(get_room_service)],
):
    return await service.create(hotel_id, data)
```

require_catalog_write здесь — обозначение будущей проверки полномочий, а не уже
существующая функция. Публичный GET не подключает эту зависимость.

В репозитории будут обычные SQL-методы, например:

```python
async def list_public_by_hotel(self, hotel_id: UUID) -> list[Room]:
    stmt = (
        select(Room)
        .join(Hotel, Room.hotel_id == Hotel.id)
        .where(
            Room.hotel_id == hotel_id,
            Room.is_active.is_(True),
            Hotel.is_active.is_(True),
        )
        .order_by(Room.id)
    )
    return list((await self.session.execute(stmt)).scalars().all())
```

Коммит делает сервис через session.begin(), а не репозиторий. Если карточка отеля
собирается из нескольких репозиториев, они получают одну сессию и работают внутри
одной операции HotelService. Вложенный вызов другого сервиса со своим begin()
на уже открытой транзакции создавать не нужно.

Для ответов лучше явно собирать схемы либо загружать связи заранее. Обращение
к незагруженному hotel.rooms при сериализации AsyncSession может вызвать
неожиданный запрос к БД и ошибку асинхронной загрузки.

## 8. Поиск, стили и цели бронирования

SearchQuery принимает city, check_in, check_out, guests_count, rooms_count,
interior_style, booking_purpose, tags, sort, page, limit.

Проверки до обращения к БД:

- city не пустой; check_in не раньше текущей даты, check_out позже check_in;
- guests_count и rooms_count не меньше 1;
- стили и цели существуют в активных справочниках;
- sort входит в разрешённый список, например price_asc, price_desc, rating_desc;
- page >= 1, limit имеет верхнюю границу, например 100.

Коды сортировки сопоставляются с известными SQLAlchemy-выражениями. Произвольную
строку клиента нельзя подставлять в SQL ORDER BY.

Справочники /filters возвращают код и отображаемое имя. Для R1 нужны стили
«Светлый», «Минимализм», «Лофт» и цели «Отдых», «Фотосессия», «День рождения».
В frontend эти значения не зашиваются. Предлагаю связать стили и цели с Room
через таблицы связей: пользователь в итоге выбирает конкретный номер.
Обычные tags можно оставить у Hotel и Room, как в ТЗ.

Предлагаемая логика: OR внутри выбранных значений одного фильтра и AND между
разными группами. В ТЗ эта логика требует подтверждения, поэтому её нужно закрепить
как решение до реализации.

Все условия уровня номера должны выполняться **для одного подходящего номера**.
Нельзя показать отель из-за того, что один его номер имеет стиль «Лофт»,
а совершенно другой подходит для фотосессии и по вместимости.

Для выборки отелей удобно использовать EXISTS по подходящим Room/Rate либо
выборку уникальных hotel_id. total считает отели, а не строки JOIN с номерами.
Сортировка должна быть устойчивой: после цены или рейтинга добавляем hotel_id.

Сброс фильтров выполняет frontend: очищает style/purpose/tags и связанные параметры,
сохраняя город и даты, затем повторяет GET поиска. Событие reset filters передаётся
в аналитику отдельно; сам каталог не хранит постоянный объект «фильтры пользователя».

## 9. Где проверять доступность и бронировать

Каталог знает описание номера, его вместимость и тарифы. Booking/inventory знает,
сколько экземпляров свободно на даты с учётом броней и неистёкших удержаний.
Поле Rate.is_active означает, что тариф разрешён к продаже; оно не доказывает
наличие свободного номера в выбранный период.

Для первого MVP поиск можно оставить в catalog_service. Для запросов с датами
CatalogSearchService обращается к booking/inventory через AvailabilityClient.
Проверять доступность нужно пакетно, без отдельного HTTP-запроса на каждый номер.

До появления этого источника каталог может отдавать описания и тарифы, но поиск
на даты нельзя считать завершённым или обозначать его результаты как доступные.

Важно сначала учесть доступность, затем считать total и применять пагинацию.
Если сначала взять 20 отелей, а после убрать занятые, страница и total будут неверны.
Для небольшого MVP можно пакетно проверить ограниченный городом набор кандидатов
и затем отфильтровать SQL-выборку по подходящим room_id. При росте данных понадобится
отдельная поисковая модель, индексы и продуманное обновление остатков.

Гостевой поиск тоже может вызывать внутренний availability API. Для такого
межсервисного запроса нужна отдельная служебная аутентификация: пользовательского
JWT у гостя нет. Нельзя подделывать пользователя или раздавать приватный ключ
gateway остальным сервисам ради этого вызова.

При создании брони BookingService повторно проверяет доступность и актуальную цену,
атомарно резервирует нужное количество, фиксирует цену и условия тарифа.
Результат поиска не гарантирует, что номер останется свободным до оформления.
За защиту от двойной брони отвечает booking/inventory, а не обычный SELECT каталога.

В БД бронирований сохраняются необходимые снимки: название отеля и номера,
адрес, цена, валюта и условия. UUID объектов каталога сохраняются как ссылки,
но внешнего ключа через две разные базы не будет. Деактивация или изменение
каталога не должны менять смысл уже оплаченного бронирования.

| 2 | Создать catalog_service, конфигурацию, Database, healthcheck и миграции Hotel/Room/Rate |
| 3 | Добавить seed-данные и публичные карточки отеля, номера, тарифов |
| 4 | Добавить справочники, фото, поиск по городу, тегам и параметрам номера, total и пагинацию |
| 5 | Подключить защищённые административные операции и деактивацию |
| 6 | Подключить реальную доступность на даты и проверки количества через booking/inventory |
| 7 | Довести отзывы и состав карточки до контракта R1; затем интегрировать бронирование и оплату |

Kafka для первых CRUD-операций не обязательна. Если появится отдельный поисковый
индекс или другие потребители изменений, можно добавить события hotel.updated,
room.updated, rate.updated и публиковать их через outbox после изменения каталога.

Минимальные проверки: гостевой доступ к чтению; запрет записи обычному пользователю;
создание номера только у существующего активного отеля; корректные фильтры и total;
исключение неактивных объектов; отсутствие дублей отелей из JOIN; откат транзакции
при ошибке; отсутствие ложного обещания доступности без источника остатков.
