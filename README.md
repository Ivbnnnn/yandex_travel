# Поиск и бронирование отелей — простой монолит

Ветка **main** содержит MVP на FastAPI и PostgreSQL. Микросервисная версия сохранена
в **feat/ms**, коммит `1f6467b`. В main только backend API и одна БД.

## Запуск

Из корня проекта:

```powershell
python tools/setup_local.py
docker compose --env-file .env.monolith up --build -d
```

- API: http://localhost:8000/api/v1
- Swagger: http://localhost:8000/docs
- Проверка готовности: http://localhost:8000/health

Скрипт создаёт **.env.monolith** со случайными паролями PostgreSQL, администратора
и секретами JWT/CSRF. Повторный запуск файл не перезаписывает. Ранее созданные
.env, .env.local и ключи микросервисов монолит не использует.
Email и пароль администратора находятся в ADMIN_EMAIL и ADMIN_PASSWORD этого файла.

При первом старте создаются таблицы, администратор, справочники и девять
демонстрационных отелей в Москве, Санкт-Петербурге и Казани. В каждом отеле
три категории номеров и два тарифа. SEED_DATA=false отключает отели, но сохраняет
инициализацию справочников и администратора.

Остановка с сохранением данных:

```powershell
docker compose --env-file .env.monolith down
```

Данные хранятся в отдельном томе monolith_postgres_data. Прежние микросервисные
тома не используются. Изменение пароля в файле конфигурации не меняет пароль
уже созданной PostgreSQL или существующего администратора.

## Что реализовано

- Гостевой поиск по городу, датам, количеству гостей и номеров.
- Стили, цели поездки, теги, сортировка, пагинация и total без дублей отелей.
- Справочники фильтров; stateless API поиска и приём события сброса фильтров.
- Данные отелей и номеров, URL фотографий, координаты, тарифы, условия и отзывы.
- Избранное без дублей, API сравнения двух-трёх отелей.
- Регистрация, вход, refresh, logout, профиль и деактивация аккаунта.
- Удержание номеров на время оплаты, бронирование, подтверждение и отмена.
- Idempotency-Key для бронирования и оплаты; повтор запроса не создаёт новую операцию.
- Демооплата с успехом, отказом и таймаутом. Настоящие деньги не списываются.
- История поездок, API уведомлений и их настройка в профиле.
- Отзыв после завершённого подтверждённого проживания.
- Административные операции с отелями, номерами, тарифами и фотографиями через API.
- Сохранение события reset_filters в analytics_events.

## Архитектура

```text
app/
├── api.py              HTTP-контракт /api/v1 и вызовы сервисов
├── dependencies.py     Depends: сервисы и текущий пользователь
├── middleware.py       access/refresh/CSRF → request.state.user_id
├── security.py         подпись JWT, пароли, установка cookies
├── errors.py           бизнес-ошибки и общие HTTP-обработчики
├── services/
│   ├── base.py         BaseService
│   ├── users.py        пользователи и аутентификация
│   ├── catalog.py      каталог, поиск, избранное, отзывы
│   ├── bookings.py     бронирование и демооплата
│   └── notifications.py уведомления, напоминания и аналитика
├── repositories.py     BaseRepository и предметные репозитории
├── uow.py              UnitOfWork: сессия, репозитории, commit/rollback
├── models.py           таблицы SQLAlchemy, UUID и ограничения БД
├── schemas.py          Pydantic-схемы запросов
├── seed.py             начальные данные
├── database.py         engine, sessionmaker, создание схемы
└── main.py             FastAPI, жизненный цикл, фоновая задача
```

Роут получает сервис через Depends. Операция сервиса открывает UOW, который создаёт
одну AsyncSession и репозитории на этой сессии. Для успешной записи сервис вызывает
uow.commit(). Не закоммиченная работа откатывается при выходе; сессия закрывается
всегда. Репозитории сами не делают commit. Напрямую в роуты AsyncSession не передаётся.

## Токены и middleware

JWT подписываются HS256: в монолите достаточно одного случайного JWT_SECRET.
Access и refresh имеют разные type, jti, exp и общий sid сессии. База хранит
SHA-256 refresh-токена. При refresh токен меняется под блокировкой сессии;
повторное использование прежнего refresh даёт 401.

При login/refresh **роут** вызывает TokenService.set_cookies(). В ответе появляются:

| Cookie | Назначение | HttpOnly |
| --- | --- | --- |
| access_token | Короткий доступ к закрытому API, по умолчанию 15 минут | Да |
| refresh_token | Обновление доступа, по умолчанию 30 дней | Да |
| csrf_token | Подписанное значение для X-CSRF-Token | Нет |

Middleware перед закрытым запросом проверяет подпись и тип access, сроки,
активность пользователя и состояние сессии в БД. Затем записывает UUID в
request.state.user_id, а также session_id и user_role. Сервисы не разбирают JWT.

Для изменения данных с cookies нужен разрешённый Origin и заголовок X-CSRF-Token,
совпадающий с csrf-cookie и имеющий HMAC-подпись для sid. Login/register требуют
разрешённый Origin; refresh/logout дополнительно проверяют refresh JWT и CSRF.
Refresh и logout работают без действующего access.

Для API-клиентов поддержан Authorization: Bearer с access JWT. Токен можно взять
из Set-Cookie ответа login. При Bearer CSRF не требуется: браузер не прикрепляет
этот заголовок автоматически. Refresh по-прежнему использует cookie и CSRF.
Пользовательские JWT не содержат административные полномочия: роль читается из БД.

После logout и деактивации доступ прекращается сразу, поскольку middleware
проверяет сессию в БД. Клиент при 401 может обновить токены через /auth/refresh
и повторить исходный запрос один раз.

COOKIE_SECURE=false нужен только для локального HTTP. Для HTTPS установите true.
Для запросов с cookies передавайте разрешённый Origin. При изменении адреса клиента
обновите ALLOWED_ORIGINS. По умолчанию разрешены localhost:8000 и 127.0.0.1:8000.

## Бронирование и демооплата

Room — категория одинаковых номеров; stock — количество экземпляров.
Одна бронь выбирает одну категорию и один тариф, но может запрашивать несколько
экземпляров через rooms_count. Вместимость проверяется по capacity * rooms_count.
Даты считаются интервалом [check_in, check_out): день выезда не занимает номер.

При создании брони сервис блокирует строку Room через SELECT FOR UPDATE,
проверяет остаток на всех ночах, фиксирует цену тарифа и снимок отеля/номера/условий.
Блокировка действует до коммита. Цена = тариф за ночь × ночи × количество номеров.
Истёкшие удержания не занимают остаток, даже если фоновая задача ещё не обновила статус.
Поиск и бронь используют один расчёт пикового количества занятых номеров.

Для POST /api/v1/bookings и POST /api/v1/payments нужен заголовок Idempotency-Key.
Ключ уникален в рамках пользователя и вида операции. Повтор с тем же телом возвращает
существующий объект; другое тело с тем же ключом даёт 409. Оплата берёт сумму из брони.

```json
{
  "booking_id": "UUID созданной брони",
  "payment_method": "demo",
  "payment_token": "success"
}
```

| payment_token | Результат |
| --- | --- |
| success | Платёж success, бронь confirmed, уведомление |
| fail | Платёж failed, удержание сохраняется до дедлайна для повторной попытки |
| timeout | Ответ 202 с pending; GET /payments/{id} через 2 секунды подтверждает демоплатёж, если бронь ещё действительна |

Повторный GET pending-платежа не может подтвердить отменённую или истёкшую бронь.
До дня заезда отмена подтверждённой брони делает демовозврат. Если в условиях тарифа
free_cancellation_before_check_in=false, отмена после оплаты запрещена.
Физического удаления бронирований нет. Платёжный токен и данные карты не хранятся;
payment_token — только переключатель сценария демопровайдера, а не банковские данные.

## Ограничения простого MVP

- Реального эквайринга, банковских возвратов, email/SMS и внешних поставщиков отелей нет.
- Уведомления сохраняются в БД и доступны через API. Напоминания о завтрашнем заезде
  проверяет фоновая задача раз в минуту; учитывается notifications_enabled.
- Схема создаётся через metadata.create_all на первом старте. Автоматического
  изменения существующей схемы и миграций пока нет.
- Один процесс приложения, без брокера, отдельных воркеров и поискового движка.
- Поиск рассчитывает доступность кандидатов в памяти; это решение для небольшого MVP.
- Каталог и аккаунты деактивируются, история и ссылки остаются в БД.
- Сохранение выбранных hotel_id/room_id/rate_id до входа, отображение карты и сброс
  формы фильтров — ответственность отдельного клиента. Frontend в проект не входит.
- Начальные данные не содержат файлов фотографий. Администратор добавляет URL через API.

Тесты в main не добавлены по запросу. Для тестировщика доступны Swagger и
[описание API и запуска](docs/local-development.md). Микросервисные тесты сохранены в feat/ms.
